# Contributing

Thank you for helping improve the Reopt Data SDK reference application. The
storefront exists to make integration behavior observable, so changes should
keep the SDK boundary explicit and the example easy to inspect.

## Before you start

- Use Node.js 22.22.1 or newer and pnpm 10.30.1.
- Work on the `staging` branch or a branch based on `staging`.
- Target pull requests to `main` only after the change has been validated on
  `staging`.
- Do not include real write keys, client secrets, tenant data, or captured user
  payloads in issues, commits, screenshots, or fixtures.
- Read [SECURITY.md](./SECURITY.md) before reporting a vulnerability.

Install dependencies once to activate the repository's Husky hooks:

```bash
corepack enable
pnpm install
```

## Development workflow

1. Reproduce or describe the behavior before changing it.
2. Keep the change to one logical concern.
3. Update tests and documentation with the implementation.
4. If an SDK capability changes, update `lib/reopt/feature-map.ts` and the
   capability table in `README.md` in the same change.
5. Run the local validation suite.
6. Commit using the rules below and open a pull request with the validation
   results.

The application works without Reopt credentials in fail-open mode. A real SDK
round trip requires either deployment credentials in `.env.local` or the
gitignored `.reopt-local.json` generated by `pnpm reopt:setup`.

## SDK regressions and workarounds

This repository protects the recommended integration patterns with executable
examples. If an SDK regression is suspected:

1. Record the smallest useful reproduction before introducing a workaround.
   Prefer a focused Playwright spec or a single request when possible.
2. Document the observed behavior, expected behavior, affected package, and
   exact package version.
3. If the example must carry a workaround, add a nearby comment explaining why
   it exists and which SDK version requires it.
4. Add a regression test when the failure can recur silently.
5. Remove the workaround after the fixed SDK is published and adopted. A fixed
   upstream package plus a permanent local workaround is not a completed task.

## Commit messages

All commit headers must be written in English and follow
[Conventional Commits](https://www.conventionalcommits.org/):

```text
type(scope): subject
```

The `commit-msg` hook runs commitlint. In addition to the Conventional Commits
rules, this repository rejects non-ASCII commit headers so the public history
stays consistently readable in English.

### Allowed types

- `feat`: a user-visible or SDK-example capability
- `fix`: a defect correction
- `docs`: documentation only
- `test`: test coverage or test infrastructure
- `refactor`: behavior-preserving code restructuring
- `perf`: performance improvement
- `build`: build system or dependency changes
- `chore`: repository maintenance
- `style`: formatting-only changes
- `ci`: external CI configuration, if the repository policy changes

### Header rules

- Use a short, lowercase scope such as `reopt`, `proxy`, `consent`, `devtools`,
  `shop`, `auth`, `e2e`, or `sdk-mode`.
- Write the subject in the imperative mood: `add`, `prevent`, `document`, not
  `added`, `prevents`, or `documentation`.
- Start the subject with a lowercase letter.
- Do not end the subject with a period.
- Keep the complete header at 100 characters or fewer.
- Use the body to explain **why**, including constraints and alternatives that
  are not evident from the diff.
- Use `!` and a `BREAKING CHANGE:` footer for breaking changes.

Good examples:

```text
feat(devtools): show the session credential on each batch
fix(consent): prevent double encoding in the consent cookie
docs(readme): explain request-scoped tenant resolution
```

Bad examples:

```text
updated files
Fix Bug.
feat: update stuff
```

You can test a message before committing:

```bash
printf '%s\n' 'docs(readme): clarify local setup' | pnpm exec commitlint
```

Do not use `--no-verify`. A failing hook is part of the feedback from the
repository.

## Atomic commits

- One commit should represent one logical change.
- Do not combine a behavior change with unrelated cleanup.
- Keep each commit buildable and make its relevant tests pass.
- Stage explicit paths instead of relying on `git add -A`.
- Split generated or mechanical changes when they obscure the reason for a
  functional change.

## Required validation

Run both commands before requesting review:

```bash
pnpm check
pnpm e2e
```

`pnpm check` runs formatting verification, oxlint, and TypeScript. `pnpm e2e`
runs Playwright against the local development server. With no
`.reopt-local.json`, real round-trip specs skip themselves and fail-open specs
still run.

For changes that can behave differently after compilation, also run:

```bash
pnpm build
pnpm e2e:production
```

This repository does not use GitHub Actions. Include the commands and outcomes
in the pull request so reviewers can see which local checks were completed.

## Pull requests

A useful pull request:

- explains the problem and why the chosen approach fits this reference app;
- identifies affected SDK packages and exact versions;
- links an issue or upstream defect when one exists;
- includes screenshots only when the visible UI changed;
- calls out credentials, consent, identity, caching, or fail-open implications;
- lists the local validation commands and results;
- contains no unrelated formatting or refactoring.

Maintainers may ask for a history cleanup before merge. Keep commits logical so
they remain useful after the branch is merged.
